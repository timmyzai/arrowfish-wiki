2. 节点健康状态机

2. Node Health State Machine

每个节点 (node_hosts 表 1 行 = 1 台 VM) 都有一个 status：

Each node (one row in node_hosts = one VM) carries a status:

状态含义触发条件线路池影响
StatusMeaningTriggerLine-pool impact
active正常服务—在线
activeServing normally—Online
degraded心跳沉默 5 分钟以上 OR TCP 探测失败开始诊断暂未移除
degradedHeartbeat silent > 5 min OR TCP probe failedDiagnosis startsNot yet removed
provider_temp_down探测失败 + 付费日未到判定为临时故障移除
provider_temp_downProbe fails + still within paid periodTreated as temporary outageRemoved
billing_dead探测失败 + 付费日已过 (或宽限 2h 后未知)欠费下线移除
billing_deadProbe fails + paid date passed (or unknown after 2h grace)Offline due to non-paymentRemoved
unknown_dead已知死亡但原因不明等待管理员判断移除
unknown_deadConfirmed dead, cause unknownAwaiting admin decisionRemoved
reconciling整批重装进行中BO 触发移除
reconcilingBatch reinstall in progressBO-triggeredRemoved

所有阈值都在 设置 → 节点健康 / DNS 自动化 调整，无需重启后端。

All thresholds are adjusted under Settings → Node Health / DNS Automation; no backend restart required.

3. 后台管理介面

3. Admin Interface

3.1 节点列表 — kebab 操作菜单

3.1 Node list — kebab actions menu

每行一个 ⋮ 按钮，包含 11 个操作（已分组）：

Each row has a ⋮ button with 11 actions (grouped):

  • 查看：详情 / 在线用户 / 部署日志
  • 管理：编辑 / 引导 URL / IP 池 / Mark Paid / 重装 Agent / 申请 DNS / 释放 DNS
  • 状态：暂停 / 恢复
  • 危险：软删除（红字）
  • View: Details / Online users / Deploy log
  • Manage: Edit / Bootstrap URL / IP pool / Mark Paid / Reinstall agent / Provision DNS / Release DNS
  • Status: Pause / Resume
  • Danger: Soft delete (in red)

3.2 设置 → 节点健康 / DNS 自动化

3.2 Settings → Node Health / DNS Automation

  • 健康阈值：心跳超时、探测超时、未知付费日宽限、恢复稳定窗口、临时故障告警门槛、巡检间隔（共 8 项整数）
  • 自动下线：流量阈值百分比（默认 95%）
  • DNS：GoDaddy Key/Secret、Cloudflare Token（默认隐藏，眼睛图标可显示）、托管 zone CSV、子域命名模板
  • API Key 留空 = DNS 自动化关闭。每个 Key 旁有 测试连通 按钮
  • Health thresholds: heartbeat timeout, probe timeout, unknown-paid-date grace, recovery-stable window, temporary-outage alert threshold, probe interval (8 integers total)
  • Auto-offline: traffic threshold percentage (default 95%)
  • DNS: GoDaddy Key/Secret, Cloudflare Token (hidden by default, eye icon to reveal), managed-zone CSV, subdomain naming template
  • Empty API key = DNS automation disabled. Each key has a Test connectivity button next to it

3.3 节点管理 → DNS 孤立记录清理

3.3 Node Management → Orphan DNS cleanup

  1. 页面打开自动跑干跑
  2. 列出每个 zone 的孤立记录（DB 中无、或标记为 orphan）
  3. 勾选要删除的，点 应用所选，确认后才真正删除
  4. 已释放（released）的子域永远不会被清理触碰
  1. Dry-run runs automatically when the page opens
  2. Lists orphan records per zone (not in DB, or marked orphan)
  3. Tick the ones to delete, click Apply selected; deletion only happens after confirmation
  4. Released subdomains are never touched by cleanup

4. 子域命名规范

4. Subdomain Naming Convention

默认模板：{region}{seq:02d}.{zone}，例如：

Default template: {region}{seq:02d}.{zone}, for example:

  • jp01.oportal.cc — 第 1 个日本节点
  • hk03.oportal.cc — 第 3 个香港节点
  • us2002.oportal.cc — 4 位序号也支持（模板可改为 {seq:04d}）
  • jp01.oportal.cc — 1st Japan node
  • hk03.oportal.cc — 3rd Hong Kong node
  • us2002.oportal.cc — 4-digit sequences also supported (template can be changed to {seq:04d})

子域复用规则（按地区严格）

Subdomain reuse rules (strict per region)

退役节点若 Release 时选 保留以备复用，子域进入释放池：

When a retired node is released with Keep for reuse, the subdomain goes into the released pool:

  • 新节点 → Provision DNS 时显示 「自动生成新名称」 和 「从已释放池复用」 两个 tab
  • 只能复用同地区子域（jp 释放池只能给 jp 新节点用）
  • 跨地区复用 = 手动 SQL 修改（不允许）
  • For a new node, Provision DNS shows two tabs: "Auto-generate new name" and "Reuse from released pool"
  • Only same-region subdomains can be reused (the JP released pool serves only new JP nodes)
  • Cross-region reuse = manual SQL edit (not allowed)

5. Telegram 告警规则（每个事件最多一条）

5. Telegram Alert Rules (one alert per event, max)

合并到现有 专线付款 频道。仅以下事件会发：

Merged into the existing Dedicated-line payment channel. Only these events fire:

  1. 节点进入 BILLING_DEAD：「{host} 移除：billing_dead — 影响 N 条线路。请支付发票并在 BO 点 Mark Paid」
  2. 节点进入 PROVIDER_TEMP_DOWN（持续 30 分钟未恢复）：提示可能需要联系供应商
  3. 节点进入 UNKNOWN_DEAD（2h 未知）：请管理员确认
  4. 恢复 → ACTIVE：「{host} 已恢复 — N 条线路重新上线」
  5. 抖动（1h 内 ≥ 3 次状态切换）：一条总结性告警
  1. Node enters BILLING_DEAD: "{host} removed: billing_dead — N lines affected. Please pay the invoice and click Mark Paid in BO"
  2. Node enters PROVIDER_TEMP_DOWN (no recovery for 30 min): Suggests contacting the provider
  3. Node enters UNKNOWN_DEAD (2h unknown): Asks admin to confirm
  4. Recovery → ACTIVE: "{host} recovered — N lines back online"
  5. Flapping (≥ 3 status changes in 1h): One summary alert

不会发送：5 分钟级别的心跳偶发、单次探测失败、节点常态 active 状态。

Not sent: 5-minute-scale heartbeat blips, a single probe failure, or steady-state active.

6. 部署 SOP（生产首次启用）

6. Deploy SOP (first production rollout)

  1. fea/node-driven-quota 经 MR review 后并入 main
  2. CI/CD 自动应用所有迁移到 Staging
  3. Day 1：验 node_hosts 行随 agent 注册成功；vpn_node_usages 有数据；NodeHealthReconcileJob 不会乱标
  4. Day 2：选 1 台 staging 节点 BO 整批重装 → 观察 24h
  5. Day 3-5：持续观察 TG 告警；如阈值不合适在 BO 调整（不需重启后端）
  6. Day 5+：打 production tag，CI/CD 部署到生产；维护时间窗内整批重装生产节点
  1. Merge fea/node-driven-quota into main after MR review
  2. CI/CD applies all migrations to Staging automatically
  3. Day 1: verify node_hosts rows are created on agent registration, vpn_node_usages has data, and NodeHealthReconcileJob doesn't mislabel anything
  4. Day 2: pick one staging node, run a BO batch-reinstall, observe for 24h
  5. Day 3-5: keep watching TG alerts; if thresholds need tuning, adjust in BO (no backend restart)
  6. Day 5+: tag for production, CI/CD deploys; batch-reinstall production nodes within the maintenance window
回滚路径：每个迁移都是增量（只 ADD COLUMN，没有 DROP）。回滚代码即可恢复原行为，新表保留但无人使用。所有新设置默认为 OFF 或安全值。
Rollback path: every migration is additive (ADD COLUMN only, no DROP). Rolling back the code restores the old behavior; new tables remain but go unused. All new settings default to OFF or to safe values.
